Product plan · Internal briefing

Turning a regulation into software

An interview-driven tool that walks a customer through a 33 CFR Part 101 Subpart F Cybersecurity Plan, holds the finished plan, and tells them when the law moves out from under it.

SARA and SAM already cover the collection half. The engine that would cover the rest is prototyped and passing against fixtures whose answers we knew in advance.

The idea

Three products that are secretly one

The pitch was a TurboTax-style builder for Cybersecurity Plans, plus a service that keeps a copy and alerts the client when a regulation change breaks their compliance. The response added a second audience: the same tool, pointed at auditors.

Those read as three separate builds, but in practice they are one evaluation engine invoked with different things pinned, which means most of the cost lands once rather than three times.

Where we already are

The regulatory spine is built and tested

Before any of this, the content model had to be right, because every source we were handed miscited the regulation. The spine is now checked against the PDF, and a validator gates it.

Of those 60 authorities, 48 are binding CFR text and 12 are guidance: policy letters, NVICs, work instructions, Coast Guard guides. Keeping those two apart is what stops a policy letter from blocking a customer's export.

Existing tools

Add a dropdown, not a fork

SARA and SAM are configured for RMF today. Rather than making either one MTSA-specific, they get a selectable compliance profile. SAM already has this exact mechanism for report profiles, so we are widening something that works rather than inventing one.

Everything upstream of the profile is untouched. A scraped host, a Nessus result, and a device record are the same facts whether you are answering to NIST or to the Coast Guard. Only the obligations they get measured against change.

The engine

One validator, invoked three ways

A rule is a predicate over the customer's answers, tied to a citation and carrying a severity, where a binding failure blocks an export and a best-practice failure only warns. The three products differ only in which ruleset and which set of answers you hand the engine.

ModeWho runs itWhat it answers
AuthoringThe customerWhat do I still have to do before I can file this?
AuditThe annual auditorDid this plan meet the requirements, and can I prove it later?
SurveillanceUs, for themDid a rule change just break a plan that was fine yesterday?

Feasibility, answered

Four hundred lines and no model

The obvious objection to a compliance engine in 2026 is that it wants to be a language model, and a language model is precisely what Sensitive Security Information forbids. The objection is correct, and it turned out to be moot.

The engine is built and running against the real content. It imports json, re, and datetime. Nothing else: no network call, no third-party dependency, no inference of any kind. It runs air-gapped, which is what the SSI boundary demands rather than merely tolerates.

Those seven are the regression fixtures from Sections 1 and 5, whose correct answers were written down before the engine existed. Handed the deficient plan as structured answers, the engine arrives at all seven verdicts on its own.

A rule is JSON

// The CySO must be reachable by the Coast Guard at any hour. { "id": "cyso-24-7", "authority_ids": ["cfr:101.620(b)(3)"], "severity": "binding", "predicate": { "all": [ { "eq": ["cyso.accessible_24_7", true] }, { "any": [ { "answered": "cyso.contact.mobile_phone" }, { "answered": "cyso.contact.oncall_protocol" } ]} ] } }

The language stops there: boolean combinators, presence, six comparisons, pattern and membership tests, counts, quantifiers over collections, and a single date operator. A closed set that fits on one page is a set an auditor can actually read through.

The quantifiers are what let a rule reach into SAM. The KEV check reads, in full: for every device where is_critical_system is true and the open-KEV list is not empty, require a documented compensating control.

Every verdict shows its work

EVIDENCE why cyso-24-7 failed cyso.accessible_24_7 False NOT SATISFIED cyso.contact.mobile_phone (absent) NOT SATISFIED cyso.contact.oncall_protocol (absent) NOT SATISFIED

A model could not produce that trail reliably even if the classification allowed one. The combinators deliberately keep going past the first failure, because an auditor asking what was checked is owed the whole list rather than the first thing that went wrong, and the evaluation date is passed in rather than read from the clock, so re-running a pinned plan version reproduces its report exactly. That is not for the Coast Guard, who only ever inspect the plan currently in force. It is what makes a surveillance diff mean anything: without it, a second run differs for reasons nobody can separate.

Determinism is worth having on engineering grounds well before the classification enters into it, and that it also satisfies the lawyers is convenient rather than the reason for it.

Quality gate

Bad rules cannot ship

A compliance tool that silently passes an unparseable rule is worse than no tool at all, so six kinds of broken rule were deliberately introduced to find out what would happen. All six were rejected before they reached the engine.

What was triedCaught by
Binding rule citing only a policy letterBindingness cap
equals typo buried in a filterStatic linter
Malformed regular expressionStatic linter
Two rules sharing an idRuleset check
Citation absent from the registryDangling-authority check
Invented severity levelShape check

The second row is the awkward one, because a filter over an empty list never runs its own body and no amount of testing would have caught that typo. Finding it needed a separate pass that reads rules without executing them, and every rule is now linted that way before it can be used.

Two real bugs surfaced by building it rather than describing it.

A rule escalating from best practice to binding produced zero reported changes, while quietly turning an exportable plan into a blocked one. The diff compared pass and fail but not severity, which would have left the most consequential alert we send as the one least likely to fire.

Separately, failing rules only showed the first unmet condition rather than all of them, which would have made audit reports thinner than an auditor needs. Both fixed.

The mechanism

Why we can tell the law moved

Alerting sounds simple until you ask how you know what changed. If both the plan and the rules drift, a failed check tells you nothing about whose fault it is.

Freezing the answers is what makes the question answerable. We already decided to freeze them for amendment diffs and the five-year renewal. The alerting product falls out of that decision for free.

The part nobody expects

Two required sections are just the validator's output

Read literally, two of the fourteen required sections are a record of what your compliance checks turned up: Section 11 holds the findings you resolved, and Section 12 holds the ones you decided not to.

Which means "dismiss this warning" cannot simply be a button, because a declined finding is a risk acceptance record and needs an owner, a justification, a compensating control, and a date to revisit. Handled that way, the most irritating part of a compliance tool ends up writing the section customers dread most.

The wedge

The one thing no existing tool does

Nessus severity is not the KEV catalog. A medium-severity finding can be a Known Exploited Vulnerability, while a critical-severity finding often is not one at all.

The regulation requires KEVs in critical systems to be patched or compensated without delay — no day count, no grace period. Satisfying that means joining scan results against the live CISA KEV catalog and scoping to the devices actually flagged critical. Nothing in the RMF pipeline does this today.

It also gives the alerting service a second trigger that has nothing to do with regulations: a newly published KEV matching an old scan result can break a customer's compliance overnight, with no law changing at all.

Say these out loud

Five things that will bite us

The model question comes back at ingest. Nothing in the engine needs one, but reading a Cybersecurity Plan somebody else already wrote is genuine text understanding, and that is where a convenient API will start looking reasonable to somebody. Settle now that it has to be structured extraction with mandatory human confirmation, self-hosted, and never generation, because the decision gets considerably harder once there is a working prototype to point at.

We validate the document, not the facility. We can check that a plan says the right things, but not whether multifactor authentication is actually switched on anywhere. Since the annual audit covers the plan and its implementation, that boundary has to be printed on the report itself, or the certification quietly becomes a liability. The answer is commercial rather than technical: bundle the first audit into the plan engagement, so we build it, then go verify the facility matches it. The disclosure stays on the report either way.

Ruleset updates are staffed work. Somebody has to read the Federal Register and write the rules, so the responsiveness of the alerting product is bounded by that staffing rather than by the software, and we should be careful not to sell it as automatic.

Guidance and compliance move separately. A new policy letter shifts best practice, while only codified text shifts compliance. We already carry that distinction in the data, and it has to survive into the alerts, or we burn the channel crying wolf.

Holding the plans means holding SSI, so by default we will not hold them. Surveillance appeared to require keeping completed plans, which are Sensitive Security Information, and custody at scale is a liability nobody wanted. It turns out not to require it. The engine is already a pure stdlib library with no ambient state, so the same code runs on a customer workstation; the client keeps the answer set, their agent re-evaluates when a new ruleset arrives, and what comes back is the diff shape alone, rule ids and severities, which are not SSI. Full custody survives as an opt-in tier for clients already piping data to the SOC. The cost is that alerts naming a specific asset are a custody-tier feature, so alert copy must not quietly assume data we do not have.
